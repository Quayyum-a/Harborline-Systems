Case study · Payments and ledger backend

Splitcore: moving money between people, with a record that adds up.

A backend that accepts a tip from a guest, divides it between an entertainer, a venue and a platform, records every movement in a double entry ledger and prepares the payout. It is a working prototype, not a live payments business.

Status
Prototype, test mode only
Type
Backend API and worker
Built with

Project overview

Splitcore is a NestJS backend for digital tipping and split payments in Nigerian hospitality venues. A guest pays through a hosted Paystack checkout without creating an account. The platform then divides the money between the entertainer, the venue and the platform according to an agreed rule, records the result in a ledger and queues a payout to the entertainer.

It is an API and a background worker. It has no guest or admin interface yet, so there are no screenshots. What can be inspected is the code, the database schema, the migrations, the continuous integration pipeline and a written definition of done audit that records what was and was not verified.

Business problem

When money moves between several parties, the hard part is not taking the payment. It is knowing, afterwards and with confidence, who is owed what, proving that nothing was lost or counted twice, and paying people the right amount.

Tips given to entertainers at venues are a clear example. The shares are negotiated, the amounts are small and frequent, and the people involved need to trust the arithmetic. Splitcore was built to explore a system where the split is agreed in advance, applied the same way every time and recorded so that it can be audited.

Product objectives

  • Let a guest pay without registering, starting from a QR code.
  • Divide every payment by an explicit rule, in whole units of the smallest currency, with no rounding drift.
  • Record every movement so that debits always equal credits, and make past records impossible to alter.
  • Treat payment provider webhooks as untrusted, repeatable messages.
  • Pay out only to entertainers whose identity and bank account have been checked.
  • Notice when the internal books and the payment provider disagree.

Solution architecture

The system is split into an API process and a worker process that share a PostgreSQL database and a Redis queue. The API stays fast. Anything slow or retryable happens in the worker.

API service
A NestJS application organised into modules for authentication, venues, entertainers, QR codes, guest sessions, split rules, payments, ledger, payouts, webhooks, reconciliation and health.
Worker service
A separate process that consumes BullMQ jobs: it handles webhook events, creates ledger entries and triggers payouts, so a slow provider never blocks a request.
PostgreSQL with Prisma
Fifteen models, eight enums and nine migrations. Database constraints and triggers enforce the rules that must never be broken, in addition to the application code.
Redis and BullMQ
Queue storage for background jobs and rate limiting. The application is tested with Redis both enabled and disabled.
Provider interfaces
Payments and payouts sit behind interfaces. Paystack is the first implementation, so changing provider does not mean rewriting the domain.
Delivery
Docker for local services, a Render deployment definition, Sentry for error tracking and a GitHub Actions pipeline.

Important engineering decisions

Money is stored as whole kobo and shares as basis points
Floating point numbers cannot be trusted with money. Amounts are integers and splits are expressed out of 10,000. When a split does not divide evenly, the platform absorbs the remainder so the parties never receive more than was paid.
The ledger arithmetic is pure, and the database checks it again
The code that turns a payment into ledger entries has no database access, which makes it simple to test exhaustively. The database then independently refuses unbalanced postings and refuses to update or delete any entry, so a bug in the application cannot quietly corrupt history.
Webhooks are verified, stored, deduplicated and queued
The signature is checked against the raw request body. The event is stored, checked for a previous delivery and handed to the queue, and the endpoint answers quickly so the provider does not keep retrying. Processing the same event twice has no extra effect.
Split rules need the entertainer’s agreement
A venue can propose a split, but it only takes effect once the entertainer agrees. The platform’s own share is fixed and can only be changed by an administrator. Every change is written to an audit table that also cannot be edited.
Secure by default
Every route requires authentication unless it is explicitly marked public. Logs automatically redact passwords, identity numbers and authorisation headers. The application refuses to start if its configuration is missing or malformed.
Reconciliation alerts instead of blocking
An hourly job compares the internal clearing account with the provider’s balance and logs any drift. It does not stop payments, because a monitoring fault should not halt the business.
Payout size is a deliberate choice
Payouts are made per tip and kept under a threshold chosen to avoid a bank stamp duty charge on larger transfers, and only for verified entertainers.

Selected technical implementation

Ledger accounts
Six account types: guest pending, entertainer, venue, platform revenue, platform fees and processor clearing. Every posting is a set of debit and credit entries that must sum to zero.
Integrity in SQL
Check constraints keep amounts positive and platform fees within range. Triggers reject updates and deletes on ledger entries and on split rule audit events, and assert that postings balance.
Idempotent payouts
Before creating a transfer the payout service checks whether one already exists, and ledger entries are written even while a payout is pending, so balances stay correct if a transfer is slow.
Tests
The repository contains 72 specification files covering unit tests and end to end tests for authentication, guests, QR codes, split rules, payments, queues, security middleware and error handling.
Continuous integration
The pipeline installs dependencies, generates the Prisma client, lints, builds, applies migrations and runs unit and end to end tests against real PostgreSQL and Redis service containers.

Limitations and current status

Prototype backend, tested in Paystack test mode.

  • This is a prototype. It has processed no real money and has no customers.
  • Payments and payouts have only been exercised in the payment provider’s test mode. Live mode behaviour, including transfer limits, has not been verified.
  • There is no administrator interface and no guest or entertainer front end yet.
  • Production alerting has not been confirmed to fire end to end.
  • The tests have not been re run as part of preparing this page. The pipeline definition and test files are reported as they exist in the repository.

Potential future improvements

  • An administrator surface for the ledger, payouts and reconciliation reports.
  • Guest and entertainer interfaces on top of the existing API.
  • Live mode verification, load testing and confirmed alerting before any real transactions.
  • A notification channel for payout and split rule events.
