Splitcore

Splitcore is a product for venues and entertainers: guests can reach a human-facing tipping experience from a QR code while venue teams have a separate management surface. The public repositories contain a Next.js frontend and a NestJS backend with payment, webhook, ledger and payout modules.

01 / Business problem

Why this product exists.

A QR code that opens raw API data is not a usable guest experience. Once a payment is introduced, the system also needs a defensible way to verify settlement and account for each share.

02 / Product objective

What it is trying to change.

Separate the guest-facing QR route from the venue dashboard and keep payment verification, split calculations and ledger posting on explicit backend paths.

04 / Engineering decisions

Choices worth
making explicit.

These notes describe the implementation found in the repositories—not measured product outcomes.

01

The ledger uses positive integer kobo, validates split basis points, and checks that debits equal credits before returning a posting.

02

The settlement service re-verifies payment status, amount, currency and the stored split snapshot; a single database transaction conditionally claims settlement and writes ledger and payout obligations.

03

Webhook payloads are not treated as payment truth: stored events route into settlement, which verifies with the provider. Duplicate or concurrent settlement attempts do not double-post.

05 / Selected implementation

Details you can
follow to source.

The source separates pure ledger calculation from persistence and payment-provider access. The hosted frontend currently exposes a venue sign-in screen; the private dashboard, guest QR flow and payment paths were not exercised during this review.

06 / Current status and limits

What remains
unfinished.

  • No sign-in was attempted and no QR-token endpoint was called; the latter can create a guest session.
  • No payment provider, webhook, test card, payout or production database was contacted. Repository completion notes and service documentation are not independent proof of current production readiness.
  • The backend’s integration guide requires a configured database, queue and provider test environment; those integrations were not run as part of this website work.

07 / Potential improvements

What to do
next.

  • Add a sandbox-only, non-settling walkthrough that can be reset and that never reaches live payment services.
  • Recheck deployment and backend contract status with a controlled test environment before describing live money movement.
  • Add visible operational evidence for retries, reconciliation and manual review paths.
