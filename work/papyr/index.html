Papyr: a ledger you write by hand, stored as structured data.

Project overview

Papyr is a web application for people who keep their accounts in a paper ledger and do not want to change how they work. The user writes with a finger or a stylus on a ruled page. Each stroke belongs to a cell, so what is written is organised into rows and columns instead of being a picture of a page.

The project includes authentication, ledger books with page management, a custom ink rendering engine, a three layer ledger canvas, column management and cloud persistence. Handwriting recognition is partly built and is described below.

Business problem

Many small businesses still keep records in paper ledgers. Paper is familiar and fast, but it is easy to lose, impossible to search and hard to back up. Most digital alternatives ask the owner to type into forms or spreadsheets, which changes the habit that made the ledger work in the first place.

Papyr starts from the opposite assumption: keep the writing, and add structure underneath it.

Product objectives

  • Make writing on a screen feel immediate and natural, with no visible delay.
  • Organise handwriting into a ruled grid with editable columns.
  • Save pages automatically and securely per user.
  • Convert handwritten cells into text so records can be searched and totalled.

Solution architecture

A Next.js application renders the interface and a small set of server routes, and Supabase provides authentication and the database.

Application
Next.js 14 with React 18 and TypeScript, styled with Tailwind CSS. Pages cover sign up, sign in, password reset, a book shelf dashboard and the ledger workspace.
Ink engine
A custom Canvas 2D engine that turns pointer input into smoothed, tapered strokes. It is a separate library from the interface components.
Ledger workspace
Three stacked layers: a paper layer, a grid layer and an ink layer, with HTML overlays for editable column headers and cell selection.
Persistence
Supabase PostgreSQL stores books, pages and strokes. Saves are debounced so the writer is never interrupted.
Recognition route
A server route accepts the strokes of one cell, checks the signed in user, and sends them to a handwriting recognition service.

Important engineering decisions

A custom ink engine instead of a drawing library
Writing quality decides whether people accept a digital ledger. The engine uses curve smoothing that preserves personal handwriting, simulates pressure from stroke speed when no stylus is present, renders on an animation frame loop and keeps the cost of the current stroke constant.
Strokes belong to cells
The original design was a free canvas for note taking. When the product became a ledger, the model changed so every stroke carries a cell identifier. The change was recorded as a decision and kept backward compatible, which is what makes structured data possible later.
Three canvas layers
Paper, grid and ink are separate, so the paper texture and grid are drawn once and only the ink layer changes while someone writes.
Recognition happens per cell, after a pause
A session manager groups strokes into segments and waits for a pause before asking for recognition, so the service is not called on every stroke and the writer is not interrupted.
Authentication is checked on the server
The recognition route verifies the signed in user and ownership of the book, page and cell before it accepts any strokes.

Selected technical implementation

Stroke model
Each stroke stores bezier segments with width and pressure at both ends, a creation time, bounds and an optional cell identifier.
Session manager
A tested class that collects strokes, groups them with a stroke grouper and emits events when a segment or a whole writing session is ready for recognition.
Column management
Columns can be added, removed and renamed, with automatic width, a minimum of one column and keyboard support with labelled controls.
Tests
The repository contains 23 test files written with Vitest, covering forms, the modal, the ledger components, the selection hook, the session manager, the stroke grouper and the recognition route.

Limitations and current status

Work in progress with a live demo.

  • This is a work in progress, not a finished product, and it has no customers.
  • The project’s own issue log, last updated in mid August, records a ledger canvas sizing problem on first load as open. It should be re checked on the current deployment before anyone relies on the ledger view.
  • Handwriting recognition has a server route and a client, but its results are not yet saved into cells according to the same issue log.
  • The application is described as offline first in its page metadata. I found no service worker or offline storage in the repository, so offline use should be treated as not yet built.
  • Some project documents describe earlier designs and are marked as historical. They are not a description of the current behaviour.

Potential future improvements

  • Fix and test the ledger canvas sizing on load, then capture real screenshots.
  • Save recognised text into cells and add search and column totals.
  • Offline writing with later synchronisation.
  • Mobile and stylus testing on real devices, and a cleaner repository without editor history and temporary files.
